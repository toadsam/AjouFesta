# AI 활용 기록

2026 가을축제 '바람' 버전은 Claude Code(Anthropic의 코딩 에이전트)와 같이 만들었다. 2026년 9월 7일 이후 커밋 130개 중 129개에 공동 작성자로 Claude가 적혀 있고, 이 기간 코드의 대부분은 Claude가 작성했다. 5월 대동제 버전(그 이전 커밋 183개)에는 이 표시가 없다.

이 문서는 무엇을 직접 정했고, AI가 만든 결과를 어떻게 확인했는지 적는다.

## 1. 역할

| 직접 한 것 | AI에 맡긴 것 |
|---|---|
| 만들 기능과 우선순위 결정 | 코드와 테스트 작성 |
| 현장 정보 전달(총학 확정, 주방 구성, 운영 시간) | 코드를 영역별로 읽고 위험한 곳 찾기 |
| 고칠지, 미룰지, 안 고칠지 결정 | 문서 초안, 지표 집계 |
| 운영 데이터와 배포 시점 판단 | 화면 녹화와 스크린샷 스크립트 |
| 현장에서 직접 눌러 보고 받아들일지 결정 | |

## 2. 기능을 정한 기준

기능은 현장에서 나온 불편을 보고 정했다. 테스트하면서 불편해서 바꾼 것은 [테스트-중-바꾼-것.md](테스트-중-바꾼-것.md)에 "불편했던 점, 바꾼 것, 커밋" 순서로 37건을 적었다. AI에게는 이 기록을 같은 커밋에 남기라는 규칙을 줬다.

몇 가지 예:

- **연락처 주고받기 (10월 8일)**: 첫날 성사 82쌍 중 대부분이 부스 시간을 못 잡았고, 에브리타임에 아쉽다는 글이 올라왔다. 그날 밤 만들어서 다음 날 오전에 올렸다. 서로 동의해야 번호가 가고, 되돌릴 수 없다는 걸 확인 창에 적는 것까지 정했다.
- **메뉴별 요리사 창 (10월 6일)**: 축제 전날 밤에 주방이 메뉴별로 4곳이라는 걸 알았다. 주문 단위 완료로는 어느 주방이 완료할지 정할 수 없어서 메뉴 줄마다 완료를 두게 했다. 현장에서 "각자 원하는 메뉴만 있어서 편했다"는 말이 나온 화면이다.
- **확정 정보 대조 (10월 6일)**: 총학 최종 계획안과 인스타 최종본을 직접 대조해서 결승 시간 변경, 체육대회 취소, 부스 운영 시간 차이를 찾았다.

고민했지만 바꾸지 않은 것도 이유와 같이 남겼다. 예를 들어 자리 현황판을 여럿이 동시에 쓸 때의 약점은 축제 직전이라 서버를 건드리지 않고, 확인 창과 운영 규칙(누르기 전에 새로고침)으로 막았다.

## 3. 점검과 우선순위

점검을 세 번 했다(10월 1일 보안과 부하, 10월 3 ~ 4일 소개팅 흐름, 10월 4 ~ 5일 총점검). 총점검에서는 주점, 소개팅, 스태프 화면, 배포 설정을 나눠서 AI 네 개가 동시에 코드를 읽게 했다.

문제가 수십 개 나왔다. 전부 고치지 않고 "내일 바로 운영을 시작한다면 지금 고쳐야 하는 것"만 골랐다.

1. 문자 라이브러리 예외가 안 잡혀서 문자 한 통 실패로 신청 화면이 실패로 뜨고, 약속 전 알림이 전원에게 안 가던 것
2. 테이블 이름을 바꾸면 재배포 때 메뉴, 계좌, 테이블이 초기값으로 돌아가던 것
3. 다른 폰에서 건 품절이나 바꾼 계좌를 저장 버튼이 되돌리던 것
4. 입금 대기 목록에 새 주문이 맨 위로 끼어들어 엉뚱한 주문을 입금 확인할 수 있던 것

나머지는 [축제 결산](축제-결산.md) 6장 남은 과제로 넘겼다.

## 4. 결과를 확인한 방법

AI가 "고쳤다"고 해도 그대로 받지 않고 아래 방법으로 확인했다.

- **테스트**: 테스트 파일이 3개에서 23개로 늘었다. 고칠 때마다 그 문제를 재현하는 테스트를 같이 넣었다. 문자 예외는 연결이 안 되는 주소로 실제 라이브러리를 호출해서 예외가 잡히는지 확인한다.
- **두 기기 동시 테스트**: 주문 콘솔 두 개를 띄워 한쪽에서 품절을 걸고 다른 쪽에서 저장한 뒤, 품절이 그대로 남는지 확인했다.
- **부하 시험**: 로컬에서 SSE 연결 6,000개와 가상 방문자 600명 조건으로 초당 1,104건, p95 443ms, 오류 0을 확인했다.
- **눌러 보는 매뉴얼**: `/guide/live`는 스태프 교육용이지만 테스트로도 쓴다. Playwright가 "누를 곳" 테두리만 따라 끝까지 가는지 본다. README 영상을 녹화하다가 최소 주문 금액이 생긴 뒤 주점 1단계에서 막히는 버그를 찾았다(9781e55).
- **배포 후 확인**: push 후 Railway 배포 상태를 보고, 운영 사이트를 직접 열어 바뀐 화면을 확인했다.

## 5. AI가 틀렸거나 다시 하게 한 것

- **리허설 날짜**: 소개팅 약속 가능 날짜를 10월 3 ~ 6일까지 열어 둔 것은 리허설 때문에 일부러 그렇게 둔 것이다. 점검 때마다 결함으로 나와서, 의도라는 걸 AI의 메모에 적어 다시 지적하지 않게 했다.
- **시연 데이터 정리**: 처음 만든 정리 코드는 시연 데이터 넣기가 꺼진 서버에서만 돌게 되어 있었다. 운영 서버는 켜져 있어서 가짜 분실물이 안 지워졌다. 배포 후 운영 사이트에서 확인하고 다시 고쳤다(80de96e, 4b2c1b6).
- **문서 말투**: README와 결산 문서 초안의 제목이 구호 같고 줄표가 많아서 AI가 쓴 티가 났다. 보통 문서 제목과 설명문으로 다시 쓰게 했다(18e69d7). 같은 기준으로 다른 저장소 README도 고쳤다.

## 6. 작업 규칙

AI가 저장소와 운영 서버에 손을 대는 만큼 아래 규칙을 지침과 메모에 두고 썼다.

- 강제 push, 파일이나 브랜치 삭제, `git reset --hard`처럼 되돌리기 어려운 작업은 실행 전에 먼저 묻는다.
- 운영 키, 관리자 암호, DB 암호 같은 값은 화면에 출력하지 않는다. 점검 결과는 `.claude/audit/`에 두고 저장소에 올리지 않는다.
- 운영 DB는 허락 없이 직접 고치지 않는다. 데이터 정리가 필요하면 조건에 맞는 것만 지우는 코드를 테스트와 같이 넣고, 서버가 켜질 때 돌게 한다.
- 같은 폴더에서 여러 세션이 동시에 작업했다. 다른 세션이 띄운 서버와 포트는 끄지 않고, 다른 세션의 커밋 안 된 파일은 내 커밋에 섞지 않는다. `gradlew --stop`은 다른 세션의 빌드를 끊으므로 쓰지 않는다.
- 커밋 메시지에는 무엇을 왜 바꿨는지 적는다.

## 7. 한계

- 공개 저장소에 DB 덤프 CSV와 원본 얼굴 사진이 올라가 있던 것을 10월 4일 점검에서야 찾았다. 저장소를 비공개로 바꿨지만, 처음부터 커밋 전에 걸러야 했다.
- AI 점검은 코드를 읽는 것이라 운영 규모 문제는 못 찾는다. 소개팅 부스 시간 칸이 성사 수에 비해 부족했던 것은 축제가 끝나고 숫자를 보고서야 보였다.
- 코드가 빨리 늘었다(자바 25,357줄, JS 41,391줄). `AiMatchPage.jsx` 한 파일이 3,749줄인 것처럼 나눠야 할 곳이 남아 있다.
