# 동시 주문 시험 (2026-11-13)

축제가 끝난 뒤에 쓴 테스트다. 축제 전에 검증한 것이 아니라는 점을 먼저 적는다.

## 왜 뒤늦게 썼나

주문번호는 "오늘 이 부스의 주문 수"로 만든다(`OrderService.buildOrderNo`). 두 주문이 같은 순간에 세면 같은 번호가 나온다. 그래서 `createOrder` 는 부스 행을 잠그고 읽는다(`BoothRepository.findByIdForUpdate`, 2026-10-01 커밋 1c850bef).

축제 기록부터 확인했다. 10월 7일 주문 내역 CSV(콘솔 마감 정산에서 내려받은 것, 메뉴 줄 302개)를 주문번호로 묶어 셌다.

| 항목 | 값 |
| --- | --- |
| 주문 | 142건 (완료 117 · 서빙할 것 24 · 취소 1) |
| 주문번호 | 0001 ~ 0142, 빈 번호 0 |
| 서로 다른 주문에 같은 번호 | 0건 |
| 20초 안 같은 테이블 · 입금자 · 메뉴 | 0쌍 |
| 가장 몰린 1분 | 4건 |
| 가장 몰린 10초 | 3건 |
| 같은 초에 들어온 주문 | 최대 2건 |

겹친 번호는 없었다. 그런데 같은 초에 들어온 주문이 많아야 둘이었다. 이 주문량으로는 잠금이 시험받지 않았다. 잠금이 없었어도 운이 좋으면 같은 결과가 나왔을 수 있다.

## 무엇을 했나

`backend/src/test/java/com/festflow/backend/concurrency/OrderConcurrencyTest.java`

- Testcontainers 로 PostgreSQL 16 을 띄운다. 운영 DB 가 PostgreSQL 이고, 가짜 객체로는 행 잠금이 걸리지 않는다.
- 스레드 20개가 같은 순간에 출발한다.
- 컨트롤러의 부스별 줄(`OrderController` 의 ReentrantLock)은 넣지 않았다. 서버가 여러 대여도 남는 DB 잠금만 본다.
- 대조군은 서비스 코드를 그대로 두고 `findByIdForUpdate` 만 잠그지 않는 `findById` 로 돌렸다.

## 결과

| 경우 | 보낸 주문 | 받은 주문 | 서로 다른 번호 | 겹친 번호 |
| --- | --- | --- | --- | --- |
| 잠금 있음 · 서로 다른 주문 100건 | 100 | 100 | 100 (0001 ~ 0100) | 0 |
| 잠금 없음(대조군) · 같은 조건 | 100 | 100 | 17 | 83 |
| 잠금 있음 · 한 테이블에 20건 | 20 | 5 | 5 | 0 |
| 잠금 있음 · 같은 주문을 10번 | 10 | 10번 모두 같은 주문 1건을 돌려받음 | 1 | 0 |

- 대조군은 두 번 돌려 서로 다른 번호가 14개, 17개였다. 100건이 전부 저장됐는데 번호는 그만큼만 생겼다.
- 한 테이블의 처리 중 주문 한도는 5건이다. 20건이 동시에 와도 5건만 받고 15건은 409 로 거절했다.
- 같은 주문을 10번 누른 경우는 20초 중복 창이 받았다. DB 에 남은 주문은 1건이다.

조건: 2026-11-13, Windows 11, Docker Desktop 27.3, PostgreSQL 16-alpine 컨테이너, 스레드 20, 한 번 실행. 실행할 때마다 `backend/build/concurrency-results.tsv` 에 같은 표가 남는다.

## 다시 돌리기

```bash
cd backend
./gradlew test --tests "com.festflow.backend.concurrency.OrderConcurrencyTest"
```

Docker 가 떠 있어야 한다. 전체 테스트(`./gradlew test`)는 이 4개를 더해 127개다.

## 아직 안 본 것

- 서버를 두 대 띄우고 겹쳐 보지는 않았다. DB 잠금이 남는다는 것은 설계상 그렇다는 것이고 직접 재지 않았다.
- 주방 화면의 주문 행 잠금, 좌석 차감, 연락처 동의 쪽 잠금은 이 테스트에 없다.
- CI 가 없어서 이 테스트는 사람이 돌려야 한다.
