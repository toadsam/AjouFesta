# 부하 시험 다시 재기 (2026-11-13)

2026-10-01 축제 전에 로컬에서 부하 시험을 했고 결과를 README 와 결산에 적었다(SSE 6,000개 + 가상 방문자 600명, 초당 1,104건, p95 443ms, 오류 0). 그때 쓴 스크립트와 원자료는 저장소에 올리지 않았다. 숫자만 남아 있으면 확인할 방법이 없어서, 같은 조건으로 스크립트를 새로 쓰고 다시 쟀다.

**10월 수치를 재현한 것이 아니다.** 원본 스크립트가 없어 방문자가 무엇을 얼마나 자주 불렀는지 같게 맞출 수 없었다. 아래는 2026-11-13 의 새 측정이고, 10월 수치와 나란히 비교하면 안 된다.

## 조건

- 서버: 이 저장소의 `backend` 를 `bootJar` 로 묶어 `java -Xmx1g -jar` 로 실행. 시연 데이터(`APP_INIT_DEMO_DATA=true`), 혼잡 예측 끔.
- DB: Docker 의 PostgreSQL 16-alpine, 연결 풀 24(기본값).
- 부하: 같은 컴퓨터에서 Node 22 로 실행. 서버와 CPU 를 나눠 쓴다.
- 컴퓨터: Intel Core Ultra 7 155H(논리 코어 22), 메모리 32GB, Windows 11.
- SSE 6,000개를 events · notices · booths · congestion 네 통로에 고르게 열어 둔다.
- 가상 방문자 600명이 60초 동안 부스 목록 → 공연 일정 → 공지를 차례로 부르고 0.3~0.7초 쉰 뒤 되풀이한다.
- 요청 한도(레이트리밋)는 같은 컴퓨터에서 온 요청에는 걸리지 않는다. 한도를 시험한 것이 아니다.

## 결과

| 방식 | 초당 요청 | p50 | p95 | p99 | 오류 | SSE 유지 |
| --- | --- | --- | --- | --- | --- | --- |
| 방문자 600명을 프로세스 하나에 | 660.9 | 524.8ms | 1,735.3ms | 3,628.6ms | 0 / 40,165 | 6,000 / 6,000 |
| 방문자를 프로세스 여섯에 나눠 | 1,018.5 | 364.0ms | 937.8ms | 1,352.8ms | 0 / 61,107 | 6,000 / 6,000 |

첫 줄은 틀린 측정이다. 부하를 만드는 Node 프로세스도 스레드가 하나라서, 방문자 600명과 SSE 6,000개를 한 프로세스에 몰면 서버가 아니라 스크립트가 밀린다. 방문자를 여섯 프로세스로 나누자 같은 서버에서 초당 요청이 661 에서 1,019 로 올랐다. 둘째 줄을 쓴다.

읽는 법:

- 60초 동안 요청 61,107건에 오류가 없었고 SSE 6,000개가 하나도 끊기지 않았다.
- 응답 시간의 중앙값이 364ms 다. 방문자 600명이 쉬지 않고 넘기는 조건이라 서버가 포화된 상태의 값이다. 실제 축제 첫날 가장 몰린 1분의 주문은 4건이었다.
- 방문자가 부른 것은 조회 세 가지뿐이다. 주문·가입 같은 쓰기는 넣지 않았다. 쓰기 쪽 겹침은 [동시-주문-시험.md](동시-주문-시험.md)에서 따로 봤다.

## 다시 돌리기

```bash
# 서버를 18080 에 띄운 뒤
node scripts/load/run-split.mjs --base http://localhost:18080 --sse 6000 --visitors 600 --seconds 60 --workers 6
```

결과 원문은 `scripts/load/results/` 에 있다. 실행할 때마다 컴퓨터 사양이 결과에 같이 찍힌다.

## 아직 안 본 것

- 운영 서버(Railway)에서는 재지 않았다. 로컬 수치를 운영 수치로 읽으면 안 된다.
- 서버와 부하를 다른 컴퓨터에 두지 않았다.
- 쓰기 요청이 섞인 부하, 1시간 넘는 지속 부하는 보지 않았다.
